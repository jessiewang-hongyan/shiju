# 2A 数据基础与迁移实施记录

日期：2026-11-03。范围：本地数据层实现、故障验证、存储选型。未接入编辑页、未提交发布、未部署。正式页面仍使用一期数据与逻辑。工作区以 `c2f3d11` 为基线，新增文件尚未提交；测试记录对应本任务工作区，不冒用线上提交号。

## 交付

- `dist/modules/document-model.js`：schemaVersion 2、来源实例与作品身份、码点出处、作品与工作区校验、已摘位置推导。三类来源区域为 title / author / text；插入字符没有出处。不同篇同字可独立使用，同一位置不能重复摘取。
- `dist/modules/document-migrations.js`：旧草稿／诗集纯转换、原字符串捕获、稳定迁移身份、诊断。旧数值位置按当时的正文／标题／作者边界解码；空缺标记、非 BMP 字、插入标点均保留。原始旧文档（包括旧 ID 和未知元数据）保存在 migration 中，可用 `legacyBackupOf` 取回。
- `dist/modules/document-storage.js`：独立 IndexedDB、先备份再迁移、原子提交、读回验证、revision 冲突、显式导入旧页改动、保留冲突副本、JSON 备份和恢复。
- `tests/document-v2.test.js`：14 个新增自动化用例。`fake-indexeddb` 仅为开发依赖，不进入网页运行时。
- `prototype/multi-source/`：原生浏览器验收与容量实验页；只用自动生成的实验数据库和测试数据，不读用户旧草稿。结束后清理本次实验库及临时 localStorage 键。

## 已确定的数据和存储规则

采用独立 `shiju-v2` IndexedDB 数据库，数据库版本 1。作品 `schemaVersion:2` 与数据库物理版本是不同概念。

目前有两个 object store：`workspace` 保存一个 `current` 工作区记录；`backups` 按 SHA-256 指纹保存精确的原始迁移输入或恢复前记录。工作区包含 `{draft,saved,view}`，外层包含 `formatVersion:2, revision, writerId, imports, legacyFingerprint`。外层 revision 是并发保存的权威版本；作品内 revision 留给 2B 命令层管理，存储层不擅自改变作品内容。

`commit(next, expectedRevision)` 在同一个 readwrite transaction 中检查现有版本、写入并读回验证，transaction 完成才成功。两个连接竞争同一版本时只能一个成功。失败保留调用者传入的内存对象，不修改旧 localStorage；上层仍需在 2B 显示“未保存”。不提供失败后静默转回 localStorage 的第二套后端。

首次迁移先保存旧键原字符串并校验，再转换所有作品。任何一项损坏都停止整体提交；不会跳过坏项冒称成功。中断重试不会重复诗集。已有新版损坏／未知格式时直接报错，不能拿旧版覆盖。旧数据恢复可先通过 `captureLegacy` 导出原字符串；已保存原始备份可按指纹由 `readBackup` 读出。

`legacyChanged` 只报告变化；只有明确调用 `importLegacyChanges` 才把旧页新内容存成独立作品，并保留新版草稿。`saveConflictCopy` 生成新作品 ID，在校验当前 revision 后保存副本；原草稿不受影响。`exportBackup` 导出已持久化工作区；`restoreBackup` 验证版本、备份当前工作区后再原子恢复。备份失败即停止恢复。

特殊兼容处理：

- 旧库没有可靠的稳定目录 ID，迁移来源明确标为 `legacy / snapshot-only`，不凭篇名作者猜测目录身份。
- 旧选段未存全文码点起点，保存 `bodyStartCodePoint:null`，不虚构完整正文偏移。
- 旧版没存历史图片配置，捕获当前浏览器作品相关偏好原值到 `legacyPreferences`，注明不是历史配置。2B 接入设置适配器时再校验与映射；2A 不宣称已经还原历史视觉效果。夜览偏好不进入作品快照。
- `legacyBackupOf` 返回迁移时的原内容，不能把后续编辑过的多原文作品降级为一期作品。

## 容量实验和结论

矩阵：每份作品 1／3／5／10 篇，每篇 80 或 3000 个码点；每篇裁剪前 80 或 100 字。10 篇长文场景再增加 10／50／100 份已保存作品。数据含非 BMP 字与缺文，UUID 和完整出处均按实际结构生成。每组 IndexedDB 读写各 3 次取中位数，含校验、克隆、事务及读回。localStorage 对照各写一次并读回，配额异常照实记录。

| 场景                     | 工作区 JSON UTF-8 | 整体写入中位数 | 整体读取中位数 | localStorage 对照 |
| ------------------------ | ----------------: | -------------: | -------------: | ----------------- |
| 1 篇 × 3000 字           |          26,583 B |         1.0 ms |         0.4 ms | 成功              |
| 3 篇 × 3000 字           |          79,045 B |         2.4 ms |         0.8 ms | 成功              |
| 5 篇 × 3000 字           |         131,507 B |         4.9 ms |         1.4 ms | 成功              |
| 10 篇 × 3000 字          |         262,662 B |         7.9 ms |         2.9 ms | 成功              |
| 上述草稿＋10 份诗集作品  |       2,888,981 B |        77.8 ms |        25.4 ms | 成功              |
| 上述草稿＋50 份诗集作品  |      13,394,261 B |       344.1 ms |       117.0 ms | 配额不足          |
| 上述草稿＋100 份诗集作品 |      26,525,861 B |       685.0 ms |       236.8 ms | 配额不足          |

结论：选 IndexedDB，原因是容量和原子版本比较，不是声称每次写入都比 localStorage 快。目前整工作区提交适合迁移／备份恢复；实验暴露出诗集随自动保存整体重写的问题。

**2B 接入自动保存前必须把作品存储拆为按 documentId 的记录和轻量工作区元数据**，提供只更新当前作品的事务接口，并用 100 份作品重跑容量实验；不得直接把当前整工作区 `commit` 接到每次摘字或输入事件。必要时升级数据库物理版本并迁移已有 2A 实验记录，保留备份及 revision 冲突保障。

10 篇长文作品若复制 100 份完整历史 JSON，序列化文本约 26.26 MB；这不是 JS 堆峰值。2B 撤销应使用结构共享／命令差量，不沿用整体 JSON 快照。此实验不包括实际 DOM、字体、复杂纸纹、布局缓存、图片导出、移动端内存峰值；不能据此设置产品最大篇数，也不能视为移动端性能结论。迁移副本／原始备份的额外占用不包含在上述新建作品矩阵中。
