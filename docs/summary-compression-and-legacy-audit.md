## 实现与可维护性

`scripts/compress-summaries.mjs INPUT NEW_OUTPUT` 在全新目录生成候选。摘要采用现有 `gzip-base64-v1` 格式；不划算的小块仍保留普通 JSON。复用 Worker 现有解压器和 8 MB 解码缓存，不新增数据读取请求。解压器首次下载提前到目录摘要首次读取。

摘要文件名按内容 hash 生成；源清单目录与索引目录使用新版本路径，正文描述的版本一致更新，避免同 URL 返回不同版本的清单。正文块 ID、哈希、记录顺序、数字型 body 引用、题目/作者/预览文本均保持。输入目录不修改，已有输出目录拒绝覆盖。

同时更新全量验证、后续扩库、重建索引脚本，让它们能读取普通或压缩摘要。基准脚本将解压器下载记入首次实际需要它的目录阶段，避免转移时间后误报搜索提速。

## 当前线上版本是另一组依赖

本地保存的正式包运行时为 `15a52e2940ed593e`。与本轮前一候选文件清单对照，它有 30,199 个路径未被候选保留，共 460,562,007 B，其中 static-data 为 460,313,443 B，其余是带版本脚本、模块、样式。本轮新候选同样没有复制这套旧版本目录。

审计证据 `release-artifacts/summary-legacy-audit.json`。这是本地保存的生产清单对照，并非重新抓取当前公网站点；正式发布前仍需确认线上版本没有变化。

因此“保留 293 MB 兼容数据”不等于“当前线上已经打开的页面也兼容”。若既保留 293 MB，又补齐当前正式版资源，本候选会约 1.276 GB；即使先退休最旧兼容层再补当前正式版，仍约 983 MB，余量很小。

## 建议的迁移方案（尚未实施）

1. 先确定支持窗口：正常新打开页面支持最新版；历史常驻标签页支持有限时间并提示保存后刷新，不承诺永不刷新。上线前验证草稿、诗集和自定义文本的保存与刷新恢复，不自动清空数据或强制刷新。
2. 在仍使用当前生产数据的一次过渡版本中加入版本变化/旧资源失效时的明确更新提示，并保留原数据。在新旧标签页中模拟发布后继续搜索、打开原文和恢复创作。已加载的更早 JS 不会因为新部署就自动获得提示，因此仍需决定其退出日期；仅等待若干天不证明无人使用。
3. 为最旧整库、分片和两种索引建立明确的构建兼容清单与到期版本；授权实施退役后一起移除对应旧入口和数据。许可文本、可恢复的发布快照和固定正文提交独立保留。不要靠发布时手工删目录。
4. 当前正式版 460 MB 搜索资源不能无限叠加。若必须让已打开页继续无感搜索，需要旧 URL 的托管或转发方案并实测；把文件移到另一个 Git 仓库并不会让旧请求自动改地址。否则采用保存后刷新策略，并进一步缩小新索引以保留所需短期过渡空间。
5. 只有新打开页面、当前正式版常驻标签页、支持窗口内旧版、草稿恢复及回滚均验收后，才发布精简包。本轮仅交付审计和方案，不执行过渡发布或退役。

## 复现

```sh
node scripts/compress-summaries.mjs release-artifacts/ming-qing-final-data NEW_DATA
RELEASE_DATA_DIR=NEW_DATA RELEASE_OUT=NEW_SITE RELEASE_PREVIEW_BODY_BASE=http://127.0.0.1:4194/bodies/ RELEASE_INVENTORY=NEW_INVENTORY node scripts/build-release.mjs
RELEASE_DATA_DIR=NEW_DATA RELEASE_OUT=NEW_SITE RELEASE_SEARCH_FIXTURES=release-artifacts/ming-qing-input/search-fixtures.json RELEASE_VERIFICATION=NEW_VERIFICATION node --max-old-space-size=4096 scripts/verify-release.mjs
RELEASE_DATA_DIR=NEW_DATA RELEASE_OUT=NEW_SITE RELEASE_PERFORMANCE=NEW_PERFORMANCE node scripts/benchmark-release.mjs
```

NEW_* 为独立输出，避免覆盖已保留的生产及基准证据。正式部署须另行固定新数据提交、去除 localhost 预览参数并完成兼容迁移验收。
