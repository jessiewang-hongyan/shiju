# 静态搜索：移动弱网与发布体积评估

> 后续已完成高命中单字及转换库优化，最新复测见 [优化报告](static-search-hot-optimization.md)。下文为优化前基线。

日期：2026-10-29。仅本地测试，未部署、未推送。结论：常规查询可用，但首次等待仍偏长，高命中单字是上线前必须处理的边界；不可将当前实验数据直接追加到 dist 发布。

## 测试方法与边界

- 真实 `metadata-engine.mjs` 执行查询；在资源读取层按 gzip 字节数模拟传输，每个请求增加一轮 RTT，并发响应共享单条下行带宽（20 ms 调度）。不是将每个请求都按独享带宽计时。
- 三档为人为定义的测试参数，不代表特定运营商网络：1,600 kbps/150 ms；800 kbps/300 ms；400 kbps/600 ms。
- 每组用新引擎先打开文集列表，再首次查询、重复查询、下一页和原文加载。首次关键词查询含 OpenCC 下载；打开文集的等待另外列出。不开启持久 HTTP 缓存。
- 使用桌面 CPU；未模拟手机 CPU、TLS/DNS、真实丢包、无线调度、Safari 内存回收。单次样本不是 p95/SLA，不能称为 iPhone 真机性能。
- 浏览器另用 390×844 视口和受限静态文件服务器实际检查，800 kbps/300 ms 下赤壁赋显示 62 篇、苏轼前后赤壁赋居前；点击前赤壁赋约 1.35 秒显示 5 段全文。截图 `/tmp/shiju-mobile-weak-search.png`。

## 定时传输测试结果

单位：秒。源码与完整数字见 `prototype/static-search/benchmark-weak.mjs`、`benchmark-weak.json`。

| 参数                | 打开文集 | 赤壁赋首次 | 宋·作者苏轼首次 | 宋·春首次 |
| ------------------- | -------: | ---------: | --------------: | --------: |
| 1,600 kbps / 150 ms |      1.3 |        5.3 |             5.3 |       7.5 |
| 800 kbps / 300 ms   |      2.5 |       10.5 |            10.4 |      14.7 |
| 400 kbps / 600 ms   |      4.8 |       20.9 |            20.6 |      29.3 |

首次列为打开文集后到关键词结果完成的阶段，不能忽略“打开文集”列；也不包含编辑页 HTML/JS 启动。重复同查询原始 JSON 缓存命中，零数据请求，桌面逻辑耗时低于 0.04 秒（不代表手机整页响应时间）。

800 kbps 下赤壁赋下一页约 1.74 秒、打开原文约 1.25 秒；春下一页约 3.36 秒。400 kbps 下分别为 3.38、2.49、6.65 秒。苏轼下一页已在已加载摘要块内，无新增请求。各档结果及重复查询一致、原文可读。

最大候选字“其”匹配 144,468 条候选，单个分片 8.74 MB 原始 JSON / 1.77 MB gzip。400 kbps 下光该分片的理想传输就超过 35 秒，尚未计入转换库、摘要及往返。现有单次请求超时为 35 秒。390×844 浏览器 + 400 kbps/600 ms 静态服务器已实际复现“搜索超时，请重试”，截图 `/tmp/shiju-mobile-weak-timeout.png`。超时后改为“赤壁赋”能恢复到 62 篇结果，旧超时状态未覆盖新结果。不能把普通三组成功当成所有查询通过。

## 静态发布文件清单

脚本 `prototype/static-search/audit-package.mjs` 按当前版本去重枚举实际依赖文件，结果及逐文件列表见 `package-audit.json`。不是创建了可部署 ZIP：正式打包仍需注入静态入口、处理 /shiju/ 子路径、保留许可证并验收所有资源 URL。

这里 MB/GB 采用十进制；GitHub 的 1 GB 限额以官方执行口径为准。估算时按 1,000 MB 留余量，不按 gzip 大小替代磁盘体积。

| 组成                                        | 文件数 | 原始大小 MB |
| ------------------------------------------- | -----: | ----------: |
| 编辑器、字体和纸张等（现有 dist 排除 data） |    523 |      216.64 |
| 查询目录                                    |      1 |        0.27 |
| 去重后候选分片                              |  6,659 |      326.54 |
| 原文分片清单                                |     19 |        0.29 |
| 摘要块                                      |  3,476 |       74.85 |
| 原文块                                      |  3,476 |      225.24 |
| 新搜索运行时                                |      4 |       0.009 |
| 合计                                        | 14,158 |  **843.83** |

6752 个字符条目对应 6659 个不同文件，部分字符候选完全相同，因此本表比按条目累计的 326.85 MB 更小。整套文件逐个 gzip 合计约 363.88 MB，这是全部文件累计传输估计，既不是单个用户首次流量，也不是站点存储配额。

若保留旧 dist/data（292.78 MB）再追加新版，合计 **1,136.61 MB**，超过 Pages 的 1 GB 上限。正式版本必须替换旧索引/正文副本，而不是叠加；历史生成目录、评估脚本和 rank 块不应入包。

现有完整字体 TTF/WOFF2 文件合计 **142.08 MB**；实际字体加载器读取 manifest 和分片，不读取完整字库（配置中仍有旧 file 字段）。如果打包阶段排除这些完整副本、继续保留所有分片及授权文档，体积可进一步到约 **701.76 MB**。本次只评估，没有删除源文件；最终须对所有字体和导出补做打包产物验收。

GitHub 官方限制：发布站点最大 1 GB、每月带宽软上限 100 GB。来源：[GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)，2026-10-29 查阅。站点达到 844 MB 虽未越界，留给新文集、历史版本和构建调整的空间有限，不宜据此直接上线。

## 建议的下一步顺序

1. 先降低首查成本：精简搜索用繁简转换词典/复用已有转换库；常见单字按文集或二级范围拆分，避免所有查询都下载全库该字候选；减少首屏摘要跨块请求。
2. 用明确的发布清单替换旧 data，排除未被运行时使用的完整字库，保留许可证；检查项目子路径和所有字体、纸纹资源。
3. 重测常见单字的超时/重试/快速改词，并做 iPhone 真机与真实弱网验收。达到可接受首查时间后再决定上线。
