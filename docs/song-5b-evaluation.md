# 5B 宋库接入评估

日期：2026-10-28。基线为已发布 `e231436`。本次只生成独立评估产物并测量，未修改 dist、文集入口或线上服务。

## 结论与上线方案

**宋库可以继续走纯静态方案，但不建议原样追加。考虑后续明清及百万级数据，优先评估“独立搜索服务＋按篇加载原文”的原型；下列静态优化作为不引入服务时的备选。** 暂不需要后端搜索服务；本次计算耗时并非主要瓶颈。明、清、明末清初仍单独评估，不能沿用宋库结论。

1. **先分离构建数据和发布产物。** 完整源 JSON 留在构建缓存或拆开的审计输入中，运行时仅发布正文分片及两套索引；新增的 156 MB 合并 JSON 不进普通 Git。发布工作流根据清单组装站点，加入总大小和单文件门禁。旧版本正在使用的哈希资源先保留，不能一次性删除历史索引。
2. **保留两套索引和默认篇名作者搜索。** 新入口暂名“宋”，对应源分类；现有“宋词”独立。四种字段与文集筛选继续叠加，不按作者拆成互斥文集，也不把全文搜索藏掉。
3. **列表改用轻量结果摘要。** 摘要只包含显示用的篇名、作者、首句、提示及原文定位；选择作品时再读取正文，预览确认后进入创作。要保持出处、重复版本、缺文提示，不能直接把摘要当正文使用。需要原型复测，尚未声称优化后下载量达标。
4. **给索引与正文缓存设置容量限制。** 按近期使用淘汰已完成请求；在途请求仍合并，失败可重试。避免一次会话不断累积所有索引桶和正文。容量按解码后对象开销评估，不能只看 gzip 字节；先以桌面 40 次查询 retained heap 增量不超过 64 MB、全库不超过 128 MB 为工程目标，之后用 iPhone 真机确认。
5. **宋库独立上线。** 上线前重新执行全部数据与编辑导出验收、同一组搜索基准、冷缓存/重复查询/慢网/失败重试/手机测试。建议发布产物低于 800 MB，为后续版本留余量；样例首屏检索传输量目标不超过 1 MB，20 Mbps + 100 ms RTT 下首屏目标 2 秒内。这些是待验收目标，不是本轮实测结论。前两项优化应先单独上线，再发布宋库；不要同时接入后续明清库。

发现：

- 宋库两套索引的典型查询计算均较快；小索引“苏轼”仅索引约 419 KB，全文约 699 KB，减少约 40%。
- 小索引“明月”虽然只匹配 97 条，前 40 条分散在 33 个正文分片，总计 36 请求、2.26 MB。原文按源顺序分片使稀疏结果放大下载量；小索引减少检索负担，并不保证整个首屏总量更小。
- 2.26 MB 在 5 Mbps 下仅理想净传输就至少约 3.6 秒；还没计算延迟、重试和解析。需要摘要分片改善列表加载，单纯调整桶数不能解决。
- 全库查询请求数上升到 55–66；当前全局并发上限 4，在高 RTT 网络下可能有明显排队。建议先保持并发保护，减少所需资源数后再测，不直接无限增加并发。
- 重复同一查询命中缓存接近零计算；暖桶但重新执行匹配仍有成本。原始 JSON 保存每次测量，不用单个最佳值代表性能。

## 连续检索与内存

单独进程在一次初始查询/暖缓存对照后，连续检索 40 个常见作者、词牌、单字，每次加载前 40 条；这是缓存积累压力测试，不是典型用户行为预测。此项仅完整比对初始查询，追加 40 次用于压力观察。

| 模式 | GC 后堆增量 | 观测堆高点 | 进程 RSS 高水位 | 累计请求 |
| --- | ---: | ---: | ---: | ---: |
| title-author | 32.0 MB | 53.3 MB | 145.7 MB | 136 |

堆高点是在读取/查询边界采样，可能漏掉瞬时峰值；RSS 包含 Node 运行时，不是浏览器标签页内存。完整扫描校验在内存指标读取之后进行，避免把整库扫描占用算入索引。当前 Map 缓存没有容量上限，因此长会话仍会继续增长。此次未做 iPhone 真机或真实弱网测试，不能据此宣称移动端已达标。

## 用户追加方向：独立搜索服务（2026-10-28）

结论：可行，并且比继续让手机承载全部索引更适合后续大规模扩展。本轮只做方案说明，没有部署服务、选择付费产品或测得服务端性能。API 方案边界参考 api-engineer 技能；当前没有必要初始化外部工作区或发布接口契约。

### 建议的数据流

1. 用户选择文集、四种搜索范围并输入关键词，网页将这些检索条件发送给搜索服务。默认仍是篇名与作者。
2. 服务返回一页结果：稳定的作品 ID、数据版本、题目、作者、原分类、缺文提示和短摘要；只返回当前页，不返回索引或全部命中正文。分页使用稳定排序与游标；总数若采用近似值必须明确标注，不能悄悄替代现在的准确计数。
3. 结果卡片显示摘要；用户点击某篇后再请求该篇完整原文，展示连续片段选择和确认按钮。可由服务提供原文，也可返回版本化静态原文 URL；正文请求应按篇或足够小的块，避免重新引入整片下载放大。
4. 用户确认后在浏览器本地创作；字块 ID、挖空原文、纹理裁剪、撤销、草稿与图片导出继续留在前端。后续创作不依赖每次操作都访问服务。

### 与本轮测量的关系

服务化可避免浏览器下载 0.4–2 MB 查询索引以及持有索引缓存，但不会凭空消除服务器侧索引体积和计算成本。前 40 条摘要的实际响应大小和延迟仍需原型测量，不能用本轮 Node 本地时间当作服务接口延迟。数据迁出 Pages 也能解除站点体积压力；若只把计算移走、正文仍全量保留在 Pages，站点体积问题仍需单独处理。

### 必须保留的约束

- 四种字段与文集范围组合、当前连续子串/多关键词匹配语义、来源顺序与缺文标记。普通分词搜索不能未经验证就替代中文连续子串匹配。
- 稳定作品 ID 与数据版本；摘要和正文必须同版本。题目/作者不适合作为唯一 ID，来源重复与异文不能被自动合并。
- 搜索防抖、取消过期结果、分页和有界缓存；新服务还需错误提示、重试、基本限流、监测与可恢复的数据构建流程。
- 只发送搜索条件；不需要上传用户正在创作的集句或草稿。服务不可用时仍可编辑已有作品、使用精选或粘贴自定义原文。
- 需要额外部署和运行维护；具体托管方式、费用、访问地区延迟、可用性尚未评估。GitHub Pages 可继续承载网页，但搜索服务需另行部署。

### 推荐下一阶段

先做独立的本地服务原型，用现有 18 类与宋库共 443,692 条外部记录验证，暂不更改线上。先确定查询/分页/正文读取契约，再实现；比对同一组 54 次正确性查询，增加并发、弱网、故障和手机验收。测量摘要响应体积、首次结果时间、单篇原文时间、服务内存与成本后，再选择托管和正式上线。若服务成本/维护不合适，再落回本文的静态精简方案，不需要推翻已完成的数据审计。
